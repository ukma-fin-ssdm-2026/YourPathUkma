# Code Review

Цей документ містить результати аналізу кодової бази проєкту за ключовими критеріями якості, безпеки та стилю кодування.

> **Примітка щодо використання ШІ:** Це рев'ю підготовлено за допомогою ШІ (Claude): модель допомагала аналізувати кодову базу та структурувати документ. Усі знахідки й висновки верифіковано людиною.

> Примітка: API на цьому етапі навмисно реалізовано з mock-відповідями (вимога лабораторної), тому відсутність моделей і реальної бізнес-логіки не вважається недоліком. Рекомендації нижче стосуються того, що можна покращити вже зараз.

## Сильні та слабкі сторони проєкту

### 🟢 3 Сильні сторони
1. **Детальні інструкції для ШІ-агентів та командні регламенти:** Наявність `AGENTS.md`, `TeamCharter.md`, `Project-Description.md`, які чітко регулюють процес розробки, ролі, архітектурні рішення та правила використання ШІ. У файлах коду також є примітки про те, де і як використано ШІ.
2. **Налаштовані GitHub Actions:** Два робочі процеси: `ci.yml` (встановлення залежностей, `manage.py check`, тести, генерація OpenAPI зі `--validate`, перевірка актуальності закомміченого YAML, завантаження артефакту) та `pages.yml` (автоматичний деплой Swagger-документації на GitHub Pages). Додатково розгорнуто живий бекенд на Render, а в README є бейдж CI та інструкція з деплою.
3. **Ґрунтовний пакет проєктної документації:** Вимоги з RTM, user stories, ADR, threat model, UML-діаграми (компонентна, розгортання, послідовності, модель даних) і матриця трасування, що пов'язує вимоги з архітектурою. Єдиний формат помилок API узгоджено між кодом, схемою та `api-design.md`.

### 🔴 3 Слабкі сторони
1. **Прогалини в безпеці та конфігурації:** Захардкоджений `SECRET_KEY` та `DEBUG = True` у `Frontend/Frontend/settings.py`; відсутня конфігурація `LOGGING` в обох проєктах; `SECRET_KEY` на бекенді не має перевірки на наявність.
2. **Відсутність реальних тестів і статичного аналізу:** `Backend/api/tests.py` порожній, тож `manage.py test` у CI запускає 0 тестів, а єдиний «тест» — `test_init.py` з перевіркою «Hello World». Навіть для mock-ендпойнтів можна й варто перевіряти коди 200/400/404 і формат помилок. У CI немає лінтера/форматера.
3. **Розбіжності між документацією та кодом, заплутана структура:** README описує PostgreSQL і `DATABASE_URL`, але в налаштуваннях прописано SQLite, і змінна ніде не читається; для `Frontend` README пропонує `requirements.txt`, якого немає. Два окремі Django-проєкти в одному репозиторії та порожня `src/api/` ускладнюють навігацію.
