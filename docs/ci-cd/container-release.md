# Бонус №5: образ випуску та два визначення розгортання

## Реалізація

`publish-container.yml` реагує на завершення `CI`, але займає один раннер лише
після успішного запуску від push на `main` цього репозиторію. Це автоматичний
запуск, прямо передбачений бонусом №5; додаткового розкладу немає.
Workflow отримує саме `workflow_run.head_sha`, збирає образ API, перевіряє
запуск і доступність `/openapi.json`, потім публікує
`ghcr.io/ukma-fin-ssdm-2026/yourpathukma:<повний SHA>`.
Використовується `GITHUB_TOKEN` із `packages: write` тільки в завданні публікації.
Тимчасові облікові дані Docker та тестовий контейнер видаляються при завершенні.

Образ містить бекенд FastAPI з міграціями, без фронтенду. Він працює від
непривілейованого користувача. Контекст збирання містить лише явний перелік
потрібних файлів, без `.env`, Git та локальних даних. Залежності встановлюються
з наявного Linux/Python 3.12 lock із хешами; він також містить інструменти CI.
Для робочого середовища необхідні `APP_ENV=production`, `DATABASE_URL`,
`JWT_SECRET`, `MS_TENANT_ID`, `MS_CLIENT_ID` та решта налаштувань автентифікації.
Перевірка запуску використовує тимчасову SQLite, випадковий JWT-секрет і вимкнені демо-дані.

## Перерахунок після перших публікацій

Виберіть спільний період після ввімкнення workflow. Не використовуйте старе
вікно 23.10–13.11: образи тоді не публікувалися. Кінець вікна має бути після
завершення публікацій усіх включених запусків CI.

```bash
python -m scripts.container_metrics \
  --repo ukma-fin-ssdm-2026/YourPathUkma \
  --from 2026-11-17T00:00:00Z --to 2026-11-24T00:00:00Z \
  --markdown \
  > docs/ci-cd/evidence/container-comparison.json
```

Дати наведено як приклад, їх потрібно замінити фактичним періодом.
Перемикач `--markdown` записує таблицю лише в `docs/ci-cd/container-comparison.md`
цього репозиторію; довільний шлях із командного рядка не приймається.
Потрібен доступ до GitHub API через `gh auth login` або `GH_TOKEN`.
Скрипт збирає ту саму когорту push-запусків `CI` на `main` для обох визначень:

| Метрика | Зелений CI | Публікація образу |
| --- | --- | --- |
| Частота | Кількість зелених CI / тижні | Кількість успішних публікацій / ті самі тижні |
| Час змін | Перший коміт PR → перший зелений CI із цією зміною | Той самий початок → завершення успішного workflow публікації з цією зміною |
| Частота збоїв | Червоні CI / завершені CI | Невдалі ланцюжки CI → GHCR / завершені ланцюжки |
| Відновлення | Червоний CI → наступний зелений CI | Невдалий ланцюжок → наступна успішна публікація |

Для другого визначення невдалим ланцюжком є червоний CI або зелений CI з
невдалою публікацією. Червоний CI не запускає публікацію, але залишається
невдалою зміною за правилом лабораторної. Це не показник інцидентів production.
Для порівняння в обох колонках використовуються лише CI з результатом
`success` або `failure`. Скасовані запуски, `timed_out` та інші результати
виключаються з обох вибірок до отримання часових міток завдань. Їхні ID та
результати явно наведено в JSON (`excluded_ci_runs`) і Markdown-таблиці.
Це політика саме порівняння CI/GHCR; базовий скрипт `ci_metrics.py` не змінено.
Якщо після виключення немає жодного CI, порівняння не позначається повним.
Моментом публікації в розрахунку слугує `updated_at` завершеного workflow:
це наближення, трохи пізніше за сам `docker push`.
Повторні спроби представлені останньою спробою, як у базовому скрипті DORA.
Відсутність збоїв дає 0% частоти збоїв і **немає спостережень** для відновлення.

Публікація зіставляється з вихідним CI за ID і SHA у назві запуску;
`head_sha` самого workflow публікації може вже вказувати на новіший коміт.
Зелені CI без завершеної публікації перелічено в `pending_publication_ci_ids`.
Якщо список непорожній, таблиця попередня; її не слід подавати як завершене
порівняння. Інтервали черги/виконання публікації не вимірюються, тому для GHCR
ці похідні показники не виводяться. У JSON збережено метадані публікацій;
історію базового CI можна відтворити наявним `scripts/ci_metrics.py`.

## Докази для здачі

Після злиття до `main` і першого успішного запуску додайте в розділ «Бонуси»
`dora-summary.md` фактичну таблицю з `container-comparison.md`, посилання на
успішний запуск та на [пакет GHCR](https://github.com/orgs/ukma-fin-ssdm-2026/packages/container/package/yourpathukma).
До першої публікації пакет може бути недоступним. Поясніть реалізацію й обидва
визначення розгортання у відео хоча б одного учасника. Наявність конфігурації
сама по собі ще не означає виконання бонусу.

## Використання ШІ

Codex підготував контейнеризацію, workflow, скрипт і цю інструкцію.
Алгоритм зіставлення перевірено pytest (19 тестів разом із базовими метриками),
Python-код — Ruff, YAML і Bash — перевіркою синтаксису. Linux/amd64 образ
зібрано локально, міграції виконано, `/openapi.json` повернув HTTP 200.
Фактичні докази GHCR додаються після злиття.
Codex обмежив місце запису Markdown після зауваження SonarCloud S8707;
перевірка: регресійний тест CLI та повторний аналіз PR.
Codex узгодив вибірки CI/GHCR: результати поза `success`/`failure` виключаються
з обох колонок і перелічуються у звіті. Перевірка: регресійні тести CLI
для шести результатів CI, зокрема запусків без завдань, і Ruff.
