# Аналіз етапів доставки через pull request

Джерело — [часові мітки 82 PR](evidence/pr-timings.json), отримані через GitHub GraphQL API 16.11.2026 та зіставлені з [актуальними метриками](dora-metrics.json). Усі PR злито в `main`; SHA злиття збігаються з відповідними змінами. Для всіх PR отримано повну першу сторінку рев’ю (`hasNextPage=false`).

Вибірка містить **82 PR із 90 доставлених змін**. Вісім прямих релізних комітів не мають PR і не входять у цей розклад. Знаменник часток — **4 502 961 с** сумарного часу цих 82 змін; він відрізняється від знаменника графіка CI для всіх 90 змін.

## Методика

Першим рев’ю людини вважається найраніше надіслане формальне рев’ю (`submittedAt`, стан не `PENDING`) з автором типу `User`, до моменту злиття. Рев’ю ботів виключено. Звичайні коментарі, запити на рев’ю та готовність чернетки до рев’ю не вимірювалися. Тому інтервал до першого рев’ю не є чистим часом очікування рев’ю, а інтервал після нього може включати виправлення, повторні перевірки й очікування злиття.

У PR #157 відкриття й перше рев’ю передують часу авторства першого коміту, збереженому у вибірці DORA. Ці події збережено без зміни у доказах, але межі етапів обрізано на початку виміру. Від’ємні інтервали не створюються; причину такого порядку міток не встановлено.

Для PR #225 і #226 формального рев’ю людини до злиття не знайдено. Їхній інтервал від відкриття до злиття наведено окремо, без припущення про фактичне очікування рев’ю.

Злиття → зелена доставка може включати чергу, виконання й відновлення CI. Воно може перекриватися з інтервалами CI у загальному звіті, тому ці два розклади не слід додавати.

### PR #131: тривалий період чернетки й окремі блокувальні зауваження

Перше схвалення надійшло 23.10 о 07:28:38 UTC. Після нього є два коміти документації; фінальний коміт `ac4f227` має дату 23.10 07:33:42. У коментарях 23.10 о 07:50:14 та 07:56:57 наведено блокувальні зауваження до автоматизації й структури тест-плану. Це звичайні коментарі, яких не видно за одним лише станом `APPROVED`.

24.10 о 19:45:42 PR переведено в чернетку; 28.10 о 22:34:22 повернуто до рев’ю. Цей зафіксований період — **98 год 48 хв 40 с**, або **73,09%** інтервалу після першого рев’ю. Після повернення до рев’ю до злиття минуло лише **5 хв 15 с**. Результати основного CI були зеленими раніше, але SonarCloud на фінальному SHA завершився лише 25.10 о 18:47:15. Дані не пояснюють усі причини перебування в чернетці й не доводять, що зауваження були усунені саме в цьому PR.

**Пропозиція:** окремо показувати час чернетки й час після готовності до рев’ю як діагностику, зберігаючи повний час DORA; блокувальні звичайні коментарі явно відображати в підсумку стану PR.

### PR #171: повторне оновлення з main і виправлення після синхронізації

Після першого схвалення 30.10 о 08:55:31 датовано шість комітів, зокрема три оновлення з `main` 01.11. На `958df02` завдання `build` завершилося невдало: журнал містить 14 синтаксичних помилок у `src/api/main.py`. Наступний коміт `270eb63` від 01.11 18:23:55 має назву про виправлення незакритого docstring після злиття. На ньому `build` і `frontend` успішні до 18:40:30; злиття відбулося о 20:21:33, через **1 год 41 хв 3 с**. Останнє схвалення людини — о 20:21:25.

**Висновок:** у проміжку після першого рев’ю є підтверджена повторна робота й відновлення PR-CI. Скільки саме часу пішло на активні виправлення, не визначено. [Невдалий build](https://github.com/ukma-fin-ssdm-2026/YourPathUkma/actions/runs/41333227105/job/124927532762).

**Пропозиція:** після оновлення з `main` перевіряти синтаксис і основні тести до повторного очікування схвалення; окремо рахувати кількість повторних синхронізацій.

### PR #170: пізнє оновлення гілки, швидке злиття після фінального CI

Перше схвалення — 30.10 о 09:06:13. Є лише один коміт із датою після нього: оновлення з `main` 01.11 о 14:40:06 (`6b8ba3b`). Основний CI фінального SHA успішно завершився о 14:58:34; злиття — о 14:59:54, через **80 с**. На попередньому коміті `31e7b9e` основний CI вже був зеленим 30.10 о 09:03:30.

**Висновок:** довгий інтервал не пояснюється виконанням останнього CI; майже весь він передує фінальній синхронізації. Причина відкладеної синхронізації чи злиття не встановлена — у зібраній історії немає коментаря з поясненням.

**Пропозиція:** на короткому командному перегляді виявляти давно схвалені PR, які ще потребують синхронізації, та явно записувати їхні залежності чи блокери.

### PR #168: без нових комітів після схвалення

Останній коміт `d5b84c7` датований 30.10 о 08:55:26, основний CI завершився успішно о 08:57:45. Перше схвалення людини — о 09:05:41. Після нього нових комітів немає. Наступний запит рев’ю — 01.11 о 12:18:11, останнє схвалення людини — о 14:38:09, злиття — о 14:38:59.

**Висновок:** після першого схвалення минуло **53 год 33 хв 18 с** без нових комітів. У зібраних checks фінального SHA немає невдалого результату, але причина затримки до злиття невідома; це кандидат на організаційне уточнення, а не доказ бездіяльності рецензента.

**Пропозиція:** домовитися, хто супроводжує схвалений PR до злиття, та фіксувати причину, якщо його свідомо відкладають. За історією одного PR не змінювати автоматично правила злиття.

### PR #236: подальша інтеграція й повторні перевірки після схвалення

Перше схвалення — 10.11 о 17:15:04; останнє формальне рев’ю людини — того самого дня о 17:19:31. Після першого схвалення датовано дев’ять комітів, зокрема інтеграцію health-check і readiness-змін та оновлення документації. Останній коміт `6de285b` — 12.11 о 10:07:59, тобто майже через дві доби після останнього схвалення. Нового формального рев’ю людини до злиття у зібраній історії немає.

Журнали невдалих `build` на проміжних комітах підтверджують конкретну повторну роботу:

- `a527213`: Bandit B404/B603 у тесті health-check; це сталося до першого рев’ю й наведено як контекст, не як частину часу після нього.
- `26cbbb1`: `ModuleNotFoundError: No module named 'src.healthcheck'`; цей збій також передував першому рев’ю.
- `94d17cc`: перевірка `git diff --exit-code docs/api/` виявила незбережену актуальну специфікацію з `/health/ready`; це вже після першого рев’ю. Наступний коміт `02dde48` оновлює OpenAPI.

На фінальному SHA основний CI успішний до 12.11 10:10:32; злиття — о 20:18:43, через **10 год 8 хв 11 с**. Історія підтверджує зміни після схвалення й повторні перевірки, але причину останнього проміжку не пояснює.

**Пропозиція:** відокремлювати незалежні зміни в менші PR та повертати суттєво змінений після схвалення код на повторне рев’ю; перед push перевіряти генерацію OpenAPI.

### Підсумок розбору

Одна метрика «після першого рев’ю» об’єднала різні ситуації: явну чернетку (#131), повторні синхронізації та виправлення (#171), пізню синхронізацію (#170), проміжок без нових комітів (#168) і розширення змін після схвалення (#236). Тому **61,72% не можна назвати часткою очікування злиття або рев’ю**. Підтверджені факти дають підстави запропонувати розділення чернеток, супровід схвалених PR і повторне рев’ю зміненого коду; причини непояснених проміжків варто уточнити з командою. Зміни CI або правил репозиторію в межах цього аналізу не виконувалися.
