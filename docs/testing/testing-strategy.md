## 3. Плани для вищих рівнів піраміди

- **Інтеграційні.** Прогін усього набору на PostgreSQL і локально (`docker-compose`), бо SQLite не ловить помилки типів (`inet`, кирилиця в `LIKE`). Контракт: CI вже падає, якщо `docs/api/openapi-generated.*` розходиться з кодом; далі — Schemathesis проти OpenAPI. Парсер САЗ — на збережених HTML-знімках сторінок. AI-адаптер — із підміненим LLM, з перевіркою, що промпт не містить email та інших PII (ризик R1).
- **Системні (E2E).** Playwright на піднятому стеку з підміненим SSO: вхід → завантаження документа деканату → побудова плану → збереження → «Збережені плани». 3–5 критичних сценаріїв, без дублювання нижчих рівнів.
- **Приймальні.** Сценарії Given/When/Then з use-case'ів (§6 AGENTS.md) і [`user-stories.md`](../requirements/user-stories.md), прив'язані до [`rtm.md`](../requirements/rtm.md); демонстрація замовнику перед релізом етапу.

## 4. Продуктивність, безпека, property-based

- **Продуктивність:** k6, 50 віртуальних користувачів, 5 хв; умова провалу — p95 > 200 мс для каталогу й планів (з [`quality-attributes.md`](../api/quality-attributes.md)). AI-генерація — окремо, p95 ≤ 5 хв з імітованою затримкою LLM.
- **Безпека:** bandit і `npm audit` уже в CI; тести на заборону адмін-ендпоїнтів для студента (R2) є. Далі — регресійні тести на ризики з [`threat-model.md`](../architecture/threat-model.md): доступ до чужого плану/документа за id (R3), зміна `course_year` для обходу правил 4 курсу (R15), «zip-бомба» в документі деканату (R4), домен корпоративної пошти (R6); OWASP ZAP baseline проти staging.
- **Property-based:** Hypothesis для інваріантів `plan_rules` (ліміти 25 і 240 кредитів, межі навантаження), Schemathesis — генерація запитів до API за схемою.

## 5. Інтеграція в CI/CD

Зараз (`.github/workflows/ci.yaml`, кожен push і PR у `main`): ruff → bandit → перевірка OpenAPI → `pytest --cov --cov-branch --cov-fail-under=80` на PostgreSQL → артефакт `coverage-report`; паралельно frontend: `npm audit` → lint → typecheck → Vitest → build. Ruleset «Require status check» на `main` робить job'и `build` і `frontend` обов'язковими (без права обходу), тож PR з червоним CI злити не можна. Мутаційне тестування — окремий `.github/workflows/mutation.yml` (вручну, поріг оцінки за замовчуванням 60%, звіт — артефакт `mutation-report`).

| Коли | Що запускається | Мета |
|---|---|---|
| кожен PR — **є**, обов'язкові перевірки перед злиттям | лінтери, модульні + інтеграційні тести, ворота покриття | швидкий зворотний зв'язок, < 5 хв |
| злиття в `main` / нічний прогін — план | E2E Playwright, OWASP ZAP baseline | регресії між модулями |
| перед релізом / вручну (`workflow_dispatch`) | мутаційне тестування — **є** (`mutation.yml`); k6 — план | дорогі перевірки не гальмують PR |

Поріг покриття піднімаємо разом із фактичним покриттям і ніколи не знижуємо без запису в цьому документі.

## Бонуси

> Обмеження в одну сторінку на цей розділ не поширюється. Кожен пункт доповнює учасник, який його виконав.

### Ворота покриття в CI

**Поріг: 80%** покриття рядків і гілок (`--cov-fail-under=80`). Налаштування: крок «Tests with coverage report» у `.github/workflows/ci.yaml`, який запускається на кожному pull request і push у `main`; якщо покриття нижче, `pytest` завершується з кодом 1 і job `build` падає. Ruleset «Require status check» робить `build` обов'язковим, тож PR із покриттям нижче 80% злити не можна.

**Чому саме 80%.**
- Поріг обрано з запасом від реального покриття, бо середовища різняться: локально тести йдуть на SQLite і Python 3.14, у CI на PostgreSQL і Python 3.12, і покриття там коливається на частки відсотка.
- Реальне покриття 86%, тобто запас приблизно 6 пунктів: поріг ловить помітне погіршення (наприклад, новий модуль без тестів), але не блокує PR через дрібні відхилення.
- 100% не вимагається: непокриті ділянки (запуск застосунку, міграції, парсер САЗ, якого ще немає) описано в розділі 2 цього документа (таблиця «Модуль / Чому не покрито»).
- Поріг варто піднімати разом зі зростанням покриття, лишаючи запас у кілька пунктів.

**Доказ: успішний прогін.** [CI, job `build`](https://github.com/ukma-fin-ssdm-2026/YourPathUkma/actions/runs/39746149323/job/119714973136) (pull request, гілка `lab06/testing_strategy`, 2026-10-22). У логу: `Required test coverage of 80% reached. Total coverage: 86.28%`, 235 тестів пройшло. Job `frontend` у тому ж прогоні теж зелений.

**Що перевірено, що поріг справді працює.** Локально `pytest --cov=src --cov-branch --cov-fail-under=99` завершується з кодом 1, а `--cov-fail-under=80` з кодом 0. Звіт покриття лежить у [`docs/testing/coverage/`](coverage/README.md) (HTML), актуальний звіт кожного прогону CI зберігається як артефакт `coverage-report`.

### Мутаційне тестування

**Інструмент і модуль.** `mutmut 2.5.1` по `src/services/plan_rules.py` — чиста бізнес-логіка плану з покриттям 100%, тобто саме тут видно, чи тести справді перевіряють поведінку, а не лише виконують рядки. Версія 3.x не підходить: вона відкидає модулі з імпортами `src.…` (`AssertionError: Module name starts with 'src.'`), а 2.x мутує файл на місці й працює з нашою структурою (зокрема на macOS).

```bash
pip install "mutmut<3"
mutmut run --paths-to-mutate src/services/plan_rules.py \
  --runner "python -m pytest -x -q -p no:cacheprovider"
mutmut results        # список вцілілих
mutmut show 30        # diff конкретного мутанта
```

**Оцінка мутації.**

| | Мутантів | Вбито | Вижило | Оцінка |
|---|---|---|---|---|
| До доповнення тестів | 57 | 35 | 22 | **61%** |
| Після | 57 | 36 | 21 | **63%** |

Тобто за 100% покриття третина мутантів виживала — покриття показує, що рядок виконався, але не що результат перевірено.

**Мутант, що вижив (№30)** — у `check_free_elective_total`:

```diff
-    if used_in_other_years <= 0:
+    if used_in_other_years <= 1:
```

Якщо в інші роки студент використав рівно 1 кредит вільного вибору, перевірка ліміту 25 кредитів за всі роки пропускається, і план на 25 + 1 = 26 кредитів проходить (порушення AGENTS.md §4). Тести не помітили, бо передавали лише `used_in_other_years` = 0, 15 і 18 — нічого в проміжку (0; 1].

**Тест, що його вбиває** — новий кейс у `test_check_free_elective_total_with_previous_years` (`tests/test_plan_rules.py`):

```python
(25.0, 1.0, ["FREE_ELECTIVE_TOTAL_EXCEEDED"]),  # мінімальна історія теж рахується (вбиває мутанта <= 1)
```

Перевірка: `mutmut apply 30` → `pytest tests/test_plan_rules.py` дає `1 failed, 40 passed` (падає саме цей кейс); після відновлення коду весь набір зелений, повторний `mutmut run` більше не показує №30 серед вцілілих.

**Розбір решти 21 вцілілого.**

| Група | К-сть | Приклад | Рішення |
|---|---|---|---|
| Текст повідомлень і `field` | 12 | `message="XX…XX"` | свідомо не тестуємо дослівний текст: клієнт орієнтується на `code` |
| Точність округлення | 4 | `round(x, 1)` → `round(x, 2)` | еквівалентні мутанти: кредити в каталозі мають не більше одного знака після коми |
| Властивості dataclass | 3 | `frozen=True` → `False`, `field=None` → `""` | низький ризик; можна закрити тестом на незмінність `Violation` |
| Число в підказці «можна обрати не більше N» | 2 | №35 `max(0.0, …)` → `max(1.0, …)`, №36 `25 - used` → `25 + used` | **наступні кандидати**: код порушення не змінюється, але студент бачить хибну кількість доступних кредитів; вбиваються тестом на число в повідомленні |

**Місце в CI.** Повний прогін триває близько хвилини, але зростає з кількістю мутантів, тож він не входить в обов'язкові перевірки PR, а запускається вручну перед релізом: Actions → **Mutation testing** → Run workflow (`.github/workflows/mutation.yml`). Параметри: `paths` (за замовчуванням `src/services/plan_rules.py`) і `min_score` (за замовчуванням 60% — трохи нижче за поточні 63%, щоб ловити погіршення тестів, а не відомі еквівалентні мутанти). Job рахує оцінку з кешу mutmut, пише таблицю статусів у Summary прогону, падає під порогом і зберігає HTML-звіт вцілілих мутантів та JUnit XML як артефакт `mutation-report`.
