# Scavenger hunt: ризики надійності в коді

Документ створено в рамках інтерактивної активності **"Resilience Scavenger Hunt"** (Лабораторна робота 9: Надійність та інженерія стійкості).

Мета: знайти в кодовій базі `src/` місця, де система може тихо зламатися, зависнути або розкрити внутрішні деталі реалізації, та класифікувати кожен дефект за ланцюгом **«несправність (fault) → помилка (error) → відмова (failure)»** з оцінкою критичності.

---

## Категорії аналізу (Етап 1)

| Категорія | Що шукали |
|-----------|-----------|
| **A. Обробка помилок** | Відсутні `try/except`, надто широкий `except Exception`, приховані помилки, витік внутрішніх деталей |
| **B. Зовнішні залежності** | Виклики БД/API без тайм-аутів, файлові операції без резервного шляху, неперевірений зовнішній вхід |
| **C. Валідація вхідних даних** | Порожні значення, відсутність перевірки типів, відсутні граничні перевірки |
| **D. Мовчазні збої** | Повернення `None` без логування, порожні блоки `except`, відсутність чіткої помилки |
| **E. Продуктивність і блокування** | Довгі операції в обробнику запиту, потенційно нескінченні цикли, блокувальний ввід-вивід |

Метод: статичний аналіз коду за ключовими шаблонами (`except`, `pass`, `return None`, `timeout`, `sleep`, `int(`, `os.getenv`, `UploadFile`) з наступним аудитом знайдених ділянок.

## Детальний опис знахідок

### 1. Широкий `except Exception` без логування в масовому схваленні (A)

- **Файл:** [`src/api/routes/admin/sync.py:513-524`](../../src/api/routes/admin/sync.py#L513-L524)
- **Функція:** `bulk_review`

```python
for item_id in dict.fromkeys(payload.item_ids):
    try:
        with db.begin_nested():
            _review_item(db, item_id, payload.decision, admin, ip)
    except ApiError as exc:
        skipped.append(SkippedItem(id=item_id, code=exc.code))
    except IntegrityError:
        skipped.append(SkippedItem(id=item_id, code="CONFLICT"))
    except Exception:
        skipped.append(SkippedItem(id=item_id, code="INTERNAL_ERROR"))
```

- **Чому небезпечно:** Будь-який несподіваний виняток (збій серіалізації, неконсистентний стан БД, помилка транзакції) перетворюється на рядок `INTERNAL_ERROR` у списку `skipped`. Виклик `logger.exception()` відсутній, трейсбек не фіксується.
- **Потенційний вплив:** Адміністратор бачить, що частину змін пропущено, але ні він, ні інженер не можуть зʼясувати чому. Системний дефект може місяцями маскуватися за «пропущеними» елементами.
- **Класифікація (Етап 2):**
  - **Несправність (fault):** Відсутність логування трейсбеку у блоці `except Exception:` при обробці пакетного запиту.
  - **Помилка (error):** Некоректний внутрішній стан обробника: виняток проковтнуто без діагностичного сліду, контекст помилки втрачено.
  - **Відмова (failure):** Відповідь API містить непрозорий код `INTERNAL_ERROR` без пояснення; команда розробки не отримує сповіщення про внутрішній збій.
  - **Критичність:** **Середня** (запит не падає з 500, але унеможливлює діагностику і супровід модерації).

### 2. Текст внутрішньої помилки зберігається й віддається користувачу (A)

- **Файл:** [`src/parser/sync.py:218-223`](../../src/parser/sync.py#L218-L223)
- **Функція:** `run_sync_job`

```python
try:
    _execute(db, job, fetcher_factory or _default_fetcher)
except SyncFailure as exc:
    _fail(db, job_id, str(exc), exc.snapshot)
except Exception as exc:  # фонова задача не має залишити SyncJob у статусі running
    _fail(db, job_id, f"{type(exc).__name__}: {exc}")
```

- **Чому небезпечно:** Для непередбачених винятків у `SyncJob.error_message` записується сирий текст (`{exc}`): це можуть бути фрагменти SQL, шляхи до системних файлів, внутрішні типи даних. Поле віддається через публічний адміністративний API. При цьому `logger.exception` не викликається, тому повного трейсбеку в логах сервера немає.
- **Потенційний вплив:** Витік інформації про внутрішню архітектуру та стан бази даних; ускладнення діагностики, оскільки повідомлення в БД обрізається до `ERROR_MAX` без трасування.
- **Класифікація (Етап 2):**
  - **Несправність (fault):** Збереження несанітизованого `f"{type(exc).__name__}: {exc}"` у персистентне поле таблиці БД без запису стеку в журнал логів.
  - **Помилка (error):** Внутрішній технічний стан системи експонується у шар збереження даних без логування контексту виконання.
  - **Відмова (failure):** Клієнти API бачать конфіденційні технічні відомості про помилки бекенду (витік даних), а розробники не мають трейсбеку для усунення дефекту.
  - **Критичність:** **Середня** (ризик інформаційної безпеки та зниження якості супроводу).

### 3. Широкий `except` при запуску браузера та закриття ресурсів без захисту (A)

- **Файл:** [`src/parser/fetcher.py:86-97`](../../src/parser/fetcher.py#L86-L97) та [`:143-152`](../../src/parser/fetcher.py#L143-L152)
- **Функції:** `start_with_retry`, `PlaywrightFetcher.__exit__`

```python
for attempt in range(retries + 1):
    try:
        return start()
    except Exception as exc:  # Playwright кидає різні типи винятків
        last = f"{type(exc).__name__}: {exc}"
        cleanup()
        ...
```

```python
def __exit__(self, exc_type, *_exc) -> None:
    try:
        if exc_type is None and self._context is not None:
            self._refresh_session()
    finally:
        for resource in (self._context, self._browser):
            if resource is not None:
                resource.close()
        if self._playwright is not None:
            self._playwright.stop()
```

- **Чому небезпечно:** Блок `start_with_retry` перехоплює всі винятки, зберігаючи лише рядок: оригінальний виняток і його стек губляться. У методі `__exit__` закриття ресурсів не обгорнуте в `contextlib.suppress` (на відміну від `_stop`): якщо `context.close()` кине виняток, `browser` і `playwright` залишаться незакритими, а початкова помилка обходу буде замаскована новим винятком закриття.
- **Потенційний вплив:** Процеси Chromium «зависають» у памʼяті сервера й вичерпують ресурси ОС; першопричина аварії синхронізації втрачається.
- **Класифікація (Етап 2):**
  - **Несправність (fault):** Втрата оригінального винятку у `start_with_retry` та незахищений виклик методів закриття ресурсів у `__exit__`.
  - **Помилка (error):** Неповне очищення зовнішніх системних ресурсів (зомбі-процеси Playwright) і маскування первинного винятку вторинним.
  - **Відмова (failure):** Деградація пам'яті сервера через накопичення незакритих процесів браузера; адміністратор отримує заплутане повідомлення про збій закриття ресурсів.
  - **Критичність:** **Середня** (витік ресурсів ОС і ускладнена діагностика).

### 4. Запит до зовнішнього сайту без явного тайм-ауту (B)

- **Файл:** [`src/parser/fetcher.py:161-169`](../../src/parser/fetcher.py#L161-L169)
- **Функція:** `PlaywrightFetcher.fetch`

```python
def fetch(self, page: int) -> str:
    url = catalog_url(self._settings, page)

    def get() -> RawResponse:
        self._pause()
        response = self._context.request.get(url)
        return response.status, response.url, response.text()

    return fetch_with_retry(get, retries=self._settings.max_retries, delay_s=self._settings.delay_s)
```

- **Чому небезпечно:** Тайм-аут не задано ні у виклику `get(url)`, ні в конфігурації `new_context`. Тривалість очікування покладається на бібліотечні дефолти або системний TCP-стек (години). Механізм ретраїв множить це зависання на кожну спробу.
- **Потенційний вплив:** При підвисанні сайту САЗ або напіввідкритому з'єднанні фонова задача блокує робочий потік на невизначений час. Каталог залишається заблокованим у статусі `running`.
- **Класифікація (Етап 2):**
  - **Несправність (fault):** Відсутність явного параметра `timeout` у мережевому виклику `request.get(url)`.
  - **Помилка (error):** Потік виконання безстроково очікує відповіді від зовнішнього сокета (hang/deadlock).
  - **Відмова (failure):** Фонова задача синхронізації зависає на невизначений час у статусі `running`, займаючи слот у пулі задач; оновлення каталогу дисциплін зупиняється.
  - **Критичність:** **Висока** (блокування фонових потоків і зрив життєвого циклу синхронізації).

### 5. Запис файлу сесії без резервного шляху (B)

- **Файл:** [`src/parser/fetcher.py:132-141`](../../src/parser/fetcher.py#L132-L141)
- **Функція:** `PlaywrightFetcher._refresh_session`

```python
def _refresh_session(self) -> None:
    state_path = self._settings.state_path
    tmp = state_path.with_name(state_path.name + ".tmp")
    self._context.storage_state(path=str(tmp))
    os.replace(tmp, state_path)
    try:
        os.chmod(state_path, 0o600)
    except OSError:
        pass
```

- **Чому небезпечно:** Помилки файлової системи (недостатньо місця на диску, відсутність прав або блокування файлу іншим процесом під час `os.replace`) не перехоплюються. Виняток вилітає з контекстного менеджера, а тимчасовий `.tmp` файл залишається на диску.
- **Потенційний вплив:** Успішний обхід каталогу переривається аварією через другорядну дію збереження сесії; результати можуть вважатися недійсними, а залишки `.tmp` містять cookies сесії.
- **Класифікація (Етап 2):**
  - **Несправність (fault):** Відсутність ізоляції помилок файлового I/O та відсутність гарантованого прибирання `.tmp` файлу у `_refresh_session`.
  - **Помилка (error):** Переривання нормального завершення сесії винятком файлової системи та залишення тимчасового файлу зі станом.
  - **Відмова (failure):** Успішно виконана синхронізація каталогу маркується як невдала; користувач/адмін бачить повідомлення про помилку оновлення.
  - **Критичність:** **Низька** (проявляється лише при аномаліях файлової системи, але псує статус успішної задачі).

### 6. Змінні оточення без перевірки типу та меж (B, C)

- **Файл:** [`src/parser/config.py:25-33`](../../src/parser/config.py#L25-L33)
- **Функція:** `load_settings`

```python
academic_year=int(os.getenv("SAZ_ACADEMIC_YEAR", "2026")),
level=int(os.getenv("SAZ_LEVEL", "1")),
delay_s=float(os.getenv("SAZ_DELAY_S", "1.0")),
max_retries=int(os.getenv("SAZ_MAX_RETRIES", "3")),
```

- **Чому небезпечно:** Некоректне значення (`SAZ_DELAY_S="fast"`) спричиняє `ValueError` безпосередньо у момент виклику парсера, а не під час ініціалізації сервісу. Відсутні граничні перевірки: від'ємна затримка змушує відмовитися від пауз, а `SAZ_MAX_RETRIES < 0` ламає логіку повторних спроб.
- **Потенційний вплив:** Збій у конфігурації `.env` виявляється пізно та призводить до неочікуваних падінь; занадто агресивний обхід (без затримок) веде до блокування IP-адреси університету сервером САЗ.
- **Класифікація (Етап 2):**
  - **Несправність (fault):** Пряме приведення типів `int()`/`float()` без валідації формату, відсутності дефолтів при помилці та граничних обмежень (guard checks).
  - **Помилка (error):** Некоректна внутрішня конфігурація або викидання необробленого `ValueError` під час виконання бізнес-задачі.
  - **Відмова (failure):** Аварійне переривання фонової задачі синхронізації або неконтрольований шквал запитів до САЗ із ризиком блокування IP.
  - **Критичність:** **Середня** (помилка налаштування призводить до збою бізнес-функціоналу або мережевих санкцій).

    try:
        claims = jwt.decode(
            token,
            get_auth_settings().jwt_secret,
            algorithms=["HS256"],

### 12. Обробка документа у фоні без ліміту часу (E)

- **Функція:** `process_document`

```python
def process_document(document_id: int) -> None:
    with session_factory()() as db:
        document = db.get(DeaneryPlanDocument, document_id)
        if document is None:
            return
        try:
            parsed = extract_courses(document.content, document.mime_type)
            _store_courses(db, document, parsed)
            db.commit()
        except NotImplementedError as exc:
            db.rollback()
            _mark_failed(db, document_id, str(exc))
        except Exception:
            logger.exception("Не вдалося опрацювати документ деканату %s", document_id)
            db.rollback()
            _mark_failed(db, document_id, "Не вдалося розпізнати документ")
```

- **Чому небезпечно:** Обробка PDF/DOCX запускається у стандартному фоновому потоці без обмеження за часом (CPU/wall-clock timeout). «Важкий» або шкідливий файл (наприклад, декомпресійна бомба чи складні векторні об'єкти) заблокує робочий потік. Якщо процес буде перезапущено під час парсингу, документ назавжди залишиться у стані `pending` без механізму аварійного відновлення.
- **Потенційний вплив:** Вичерпання фонових воркерів; користувачі бачать «вічне очікування» обробки навчального плану без можливості перезапуску.
- **Класифікація (Етап 2):**
  - **Несправність (fault):** Відсутність таймауту на виконання розбору файлу та відсутність crash recovery для документів зі статусом обробки.
  - **Помилка (error):** Неконтрольоване зависання CPU/воркера та неконсистентний стан статусу документу в базі при перезапуску процесу.
  - **Відмова (failure):** Деградація швидкодії черги задач, відсутність відповіді для користувача про завершення розбору навчального плану деканату.
  - **Критичність:** **Висока** (зависання потоків виконання та перманентне очікування клієнта).
