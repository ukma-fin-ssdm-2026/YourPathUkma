# Звіт про надійність 

Команда: YourPathUkma. Документ підсумовує результати «Resilience Scavenger Hunt»: що знайшли, що виправили, як система поводиться під час збоїв і що лишилось відкритим.

Пов'язані документи:

- [`scavenger-hunt.md`](scavenger-hunt.md): первинний пошук ризиків (Етап 1), класифікація несправність → помилка → відмова (Етап 2) і статус виправлень (Етап 3).
- [`tests/reliability/`](../../tests/reliability/): тести надійності (30 тестів у 3 файлах).

## 3. Виправлені проблеми: до і після

Для кожного виправлення спершу обрано тип відмови: чи гірша тут неправильна відповідь, чи відсутність відповіді. Фрагменти «до» взято зі `scavenger-hunt.md`, «після» з поточного коду.

### 3.1. Знахідка №4: запит до САЗ без тайм-ауту

**Ланцюг:** несправність: виклик `context.request.get(url)` без явного `timeout` → помилка: запит висить при повільній відповіді САЗ, повтори множать очікування → відмова: `SyncJob` годинами у статусі `running`, фоновий потік заблоковано, каталог не оновлюється.

**Вибір:** швидка відмова. Неповний або застарілий обхід каталогу гірший за явну помилку, бо дані каталогу далі йдуть у чергу модерації.

Файл: `src/parser/fetcher.py`.

До:

```python
def get() -> RawResponse:
    self._pause()
    response = self._context.request.get(url)
    return response.status, response.url, response.text()
```

Після:

```python
def get() -> RawResponse:
    self._pause()
    try:
        response = self._context.request.get(url, timeout=self._settings.timeout_s * 1000)
        return response.status, response.url, response.text()
    except Exception as exc:  # Playwright кидає різні типи (TimeoutError, Error); не імпортуємо його тут
        logger.warning("Запит до САЗ не вдався (сторінка %s): %s", page, type(exc).__name__)
        raise TransientFetchError(f"{type(exc).__name__} під час запиту сторінки {page}") from exc
```

`fetch_with_retry` повторює `TransientFetchError`, 429 і 5xx не більше `retries + 1` разів з наростаючою паузою (`delay_s * 2**attempt`). Після останньої спроби кидає `FetchError`. Додатково в `src/parser/config.py` з'явилось налаштування `SAZ_TIMEOUT_S` (30 с), а в контексті Playwright встановлено глобальний тайм-аут `set_default_timeout`.

### 3.2. Знахідка №7: завантаження документа деканату

**Ланцюг:** несправність: `await file.read()` до перевірки розміру, тип за заголовком і розширенням, немає перевірки порожнього файлу → помилка: неконтрольоване споживання пам'яті, файли-підробки приймаються, порожній файл доходить до `CheckConstraint` у БД → відмова: ризик OOM від паралельних великих запитів, у БД потрапляє не-PDF, користувач бачить 500 замість зрозумілої 4xx.

**Вибір:** швидка відмова. Некоректний файл відхиляється до запису в БД і до створення фонової задачі.

Файл: `src/api/routes/deanery.py`.

До:

```python
content = await file.read()
size = len(content)

if size > MAX_UPLOAD_BYTES:
    raise ApiError(413, "FILE_TOO_LARGE", "Файл більший за 10 МБ")
...
doc_mime = mime_map.get(file.content_type)
if not doc_mime:
    if file.filename and file.filename.endswith(".pdf"):
        doc_mime = db_enums.DocumentMimeType.PDF
    elif file.filename and file.filename.endswith(".docx"):
        doc_mime = db_enums.DocumentMimeType.DOCX
```

Після:

```python
# Читаємо не більше ліміту + 1 байт: великий файл не завантажується в пам'ять повністю
content = await file.read(MAX_UPLOAD_BYTES + 1)
size = len(content)

if size > MAX_UPLOAD_BYTES:
    raise ApiError(413, "FILE_TOO_LARGE", f"Файл більший за {MAX_UPLOAD_BYTES // (1024 * 1024)} МБ")
if size == 0:
    raise ApiError(422, "EMPTY_FILE", "Файл порожній")
...
    filename = (file.filename or "").lower()
    if filename.endswith(".pdf"):
        doc_mime = db_enums.DocumentMimeType.PDF
    elif filename.endswith(".docx"):
        doc_mime = db_enums.DocumentMimeType.DOCX
    else:
        raise ApiError(415, "UNSUPPORTED_FILE_TYPE", "Дозволені лише файли PDF та DOCX")

if not _matches_signature(content, doc_mime):
    raise ApiError(415, "UNSUPPORTED_FILE_TYPE", "Вміст файлу не відповідає заявленому типу PDF або DOCX")
```

Захисні перевірки (guard clauses) йдуть у такому порядку: розмір, порожній файл, тип, магічні байти (`%PDF`, `PK\x03\x04`, для `application/msword` ще й OLE `D0CF11E0`).

### 3.3. Знахідка №8: відхилення токена без сліду

**Ланцюг:** несправність: `except (jwt.PyJWTError, ValueError): return None` без логування → помилка: система втрачає причину відхилення (термін дії, підпис, `aud`/`iss`, зіпсований `sub`) → відмова: користувач бачить загальну 401, а масове «розлогінення» після зміни `JWT_SECRET` чи атаку підбору токенів неможливо помітити.

**Вибір:** безпечна відмова. Доступ у будь-якому разі заборонено (401, як і раніше), але збій тепер видно в логах.

Файл: `src/api/tokens.py`.

До:

```python
    except (jwt.PyJWTError, ValueError):
        return None
```

Після:

```python
    except jwt.ExpiredSignatureError:
        logger.info("Токен доступу прострочено")  # штатна ситуація: клієнт оновить токен
        return None
    except (jwt.PyJWTError, ValueError) as exc:
        # Сам токен у лог не потрапляє, лише тип помилки
        logger.warning("Токен доступу відхилено: %s", type(exc).__name__)
        return None
```

Прострочений токен логується на рівні `info` (це нормальний цикл оновлення), решта на рівні `warning`. Це різні сигнали для моніторингу. Токен у лог не потрапляє.

### 3.4. Знахідка №11: обхід каталогу без межі та дедлайну

**Ланцюг:** несправність: цикл `range(2, last_page + 1)`, де `last_page` береться з HTML зовнішнього сайту → помилка: при зміні розмітки САЗ число сторінок хибне (наприклад, 100000), кожна ітерація з паузою й повторами → відмова: фонова задача працює годинами, блокує потік, навантажує САЗ (ризик бану IP).

**Вибір:** швидка відмова. Обрізаний обхід гірший за помилку: за відсутніми в обході дисциплінами система вважала б, що їх прибрано з каталогу, і створювала б хибні пропозиції `REMOVE` у черзі модерації.

Файл: `src/parser/sync.py`.

До:

```python
pages = [first]
for number in range(2, (first.last_page or 1) + 1):
    pages.append(parser.parse(fetcher.fetch(number)))
```

Після:

```python
started = clock()
...
last_page = first.last_page or 1
if last_page > MAX_PAGES:
    logger.error("САЗ повернув %s сторінок (ліміт %s): обхід скасовано", last_page, MAX_PAGES)
    raise SyncFailure(
        f"Забагато сторінок каталогу ({last_page} > {MAX_PAGES}): імовірно, змінилась розмітка САЗ", first_html
    )
pages = [first]
for number in range(2, last_page + 1):
    if clock() - started > deadline_s:
        logger.error("Обхід каталогу перевищив %s с на сторінці %s із %s", deadline_s, number, last_page)
        raise SyncFailure(
            f"Перевищено ліміт часу обходу каталогу ({deadline_s:.0f} с): оброблено {number - 1} із {last_page}",
            first_html,
        )
    pages.append(parser.parse(fetcher.fetch(number)))
```

Константи: `MAX_PAGES = 200`, `SCAN_DEADLINE_S = 30 * 60`. Годинник передається параметром `clock`, тому дедлайн перевіряється в тесті без реального очікування.

## 4. Застосовані патерни надійності

| Патерн | Де застосовано | Навіщо |
|---|---|---|
| Тайм-аут на зовнішню операцію | №4: `timeout` на кожен запит до САЗ, глобальний тайм-аут контексту Playwright | Виклик не може висіти необмежено |
| Обмежені повтори з експоненційним відступом | №4: `fetch_with_retry`, не більше `retries + 1` спроб, пауза `delay_s * 2**attempt`, без паузи після останньої | Тимчасовий збій (тайм-аут, обрив, 429, 5xx) не ламає обхід, а постійний не повторюється вічно |
| Швидка відмова (fail fast) | №4: `FetchError` після останньої спроби; №7: 413/415/422; №11: `SyncFailure` | Явна помилка краще за неповні чи хибні дані |
| Безпечна відмова (fail safe) | №8: токен відхиляється (401) і при цьому логується | Доступ закритий, збій не лишається непоміченим |
| Захисні перевірки (guard clauses) | №7: розмір, порожній файл, тип, магічні байти | Некоректний вхід відсікається до запису в БД |
| Обмежений цикл | №11: `MAX_PAGES` і загальний дедлайн `SCAN_DEADLINE_S` | Цикл не залежить від значення з чужого HTML |
| Логування без витоку секретів | №4, №8, №11 | Збій видно розробнику; токен не логується, у `SyncJob` лишається лише тип помилки |

Порядок складання патернів на одному виклику (№4): тайм-аут обмежує кожну спробу, повтори обгортають тайм-аут, а після вичерпання спроб спрацьовує швидка відмова. Резервного значення тут свідомо немає. Усі повтори обмежені: найгірший випадок для сторінки з типовими налаштуваннями (`SAZ_TIMEOUT_S=30`, `SAZ_MAX_RETRIES=3`, `SAZ_DELAY_S=1`) становить приблизно 4 × 30 с плюс паузи 1 + 2 + 4 с, тобто близько двох хвилин. Джитер у повторах не застосовано (бонус за backoff із джитером ми не заявляємо).

## 5. Режими відмов і відновлення

| № | Режим відмови | Реакція | Що бачить користувач або адмін | Як система повертається до норми |
|---|---|---|---|---|
| 4 | САЗ повільно відповідає чи обриває з'єднання | **Швидка відмова** після обмежених повторів | Адмін бачить `SyncJob` у статусі `failed` з повідомленням «Не вдалося завантажити сторінку: …» (без внутрішніх деталей) | Автоматично: повтор із наростаючою паузою. Після вичерпання спроб: адмін вручну запускає нову синхронізацію. Каталог не змінюється, бо задача завершилась помилкою |
| 7 | Завантажено завеликий, порожній або підроблений файл | **Швидка відмова** до запису в БД | Студент одразу отримує зрозумілу відповідь: 413 `FILE_TOO_LARGE`, 422 `EMPTY_FILE` або 415 `UNSUPPORTED_FILE_TYPE` | Студент завантажує коректний файл. Запису в БД і фонової задачі не створено, стан системи не змінюється |
| 8 | Токен прострочений, підроблений або зіпсований | **Безпечна відмова**: доступ закрито, збій залишає слід | Користувач бачить 401, як і раніше. Інженер бачить у логах `info` (прострочений) або `warning` (решта) з типом помилки, без самого токена | Прострочений токен клієнт оновлює через refresh-cookie. Підроблений або після зміни `JWT_SECRET`: повторний вхід. Масові `warning` у моніторингу сигналізують про проблему |
| 11 | САЗ віддає хибне число сторінок або обхід затягується | **Швидка відмова** до обробки результатів | Адмін бачить `SyncJob` у статусі `failed`: «Забагато сторінок каталогу…» або «Перевищено ліміт часу…». Зберігається знімок першої сторінки для розбору збою | Ручне втручання: адмін або розробник перевіряє розмітку САЗ, за потреби оновлює парсер або `MAX_PAGES`, після чого запускає синхронізацію знову. Каталог не змінюється, хибних `REMOVE` немає. `SCAN_DEADLINE_S` (30 хв) менший за `STALE_AFTER` (35 хв), тому задача завершується сама до того, як її позначить завислою `fail_stale_jobs` |

Зауваження до №11: дедлайн перевіряється перед кожною сторінкою, тож остання розпочата сторінка може тривати до двох хвилин. Загальний час усе одно залишається меншим за `STALE_AFTER`.

## 6. Тести надійності

Каталог `tests/reliability/` містить 30 тестів. Усі працюють без мережі: зовнішні залежності замінено тестовими дублерами.

| Тип | Файл | Що перевіряє |
|---|---|---|
| Обробка помилки (2) | `test_error_handling.py` | Несподіваний виняток у залежності дає загальну 500 `INTERNAL_ERROR` без внутрішніх деталей у тілі відповіді. Сміттєвий токен відхиляється, логується, а сам токен у лог не потрапляє (№8) |
| Ін'єкція збою (5) | `test_fault_injection.py` | Дублер імітує тайм-аут і обрив з'єднання з САЗ: повтори обмежені (3 виклики при `retries=2`, паузи 1 с і 2 с), після останньої спроби `FetchError`; тимчасовий збій відновлюється на наступній спробі; тайм-аут передається в Playwright у мілісекундах. Недоступний Microsoft дає 503 `AUTH_PROVIDER_UNAVAILABLE`, а не падіння |
| Граничні випадки (23) | `test_boundaries.py` | Файл завантаження: порожній, рівно 10 МБ, на 1 байт більше, `.PDF`/`.Docx` у верхньому регістрі, підроблені магічні байти, дозволені Word-сигнатури, невідоме розширення, межі `academic_year` (2023, 2024, 2030, 2031). ## Бонуси

### Тести надійності як обов'язкова перевірка PR

Тести з `tests/reliability/` запускаються в CI окремим кроком, і цей крок є обов'язковою перевіркою для `main`: PR не зливається за звичайними правилами, поки він не пройшов.

**Що зроблено:**
- Окремий workflow [`.github/workflows/reliability.yml`](https://github.com/ukma-fin-ssdm-2026/YourPathUkma/blob/main/.github/workflows/reliability.yml) із job `reliability-tests`, який виконує `pytest tests/reliability -q`. Тригери: push і PR у `main`, ручний запуск.
- У `.github/workflows/ci.yaml` основний крок тестів запускається з `--ignore=tests/reliability`, щоб ці тести не виконувалися двічі.
- Залежності для job ставляться лише з [`requirements-ci.lock`](https://github.com/ukma-fin-ssdm-2026/YourPathUkma/blob/main/requirements-ci.lock) (`pip install --require-hashes`): інакше SonarCloud (правило S8544) валить Quality Gate, який теж обов'язковий. Правило записано в `AGENTS.md` §9.2.
- Статус `reliability-tests` додано до обов'язкових перевірок у ruleset «Require status check», який діє на `main`. Змінено 2026-11-08 о 14:06 за київським часом.

### Перевірка здоров'я (health check) сервісу

**Що зроблено.** Додано `GET /health/ready` (`src/api/health.py`). Він паралельно перевіряє критичні
залежності: БД (`SELECT 1` через SQLAlchemy engine) і Microsoft Entra ID (запит до публічного JWKS-ендпоінта
тенанта, потрібного для входу). Кожна перевірка має тайм-аут 2 с, загальний час відповіді обмежений.
Наявний `GET /health` у `src/api/main.py` викликає ту саму функцію `readiness_check()`:
обидва маршрути перевіряють БД і Microsoft та повертають однаковий формат відповіді
зі статусом HTTP 200 або 503 залежно від доступності критичних залежностей.

**Формат відповіді.**
- Усе гаразд: `200 {"status": "healthy", "checks": {"database": {"status": "up", ...}, ...}}`
- Збій залежності: `503 {"status": "unhealthy", ...}` зі статусом `down` для проблемної залежності.
- Microsoft не налаштовано (локальна розробка): `not_configured`, це не збій.

**Режим відмови: швидка відмова (fail fast).** Збій критичної залежності не маскується резервним
значенням, а чесно повертається як `unhealthy`/503, бо моніторинг має знати про реальний стан.
Деталі збою (хост, порт, текст винятку) лише в логах, назовні їх немає.

**Відновлення.** Автоматичне: щойно залежність відповідає, наступний запит повертає `healthy`.
Окремих кроків не потрібно.
