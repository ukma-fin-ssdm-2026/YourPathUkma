## 2. Зони та межі довіри

| Зона | Опис | Рівень довіри |
|---|---|---|
| TZ-1 | Пристрій користувача: Web Browser, Client Tier (React SPA) — student UI і Admin Console | Недовірена: будь-який запит може бути підроблений |
| TZ-2 | Хостинг застосунку: Docker container «Backend» (Application Server — FastAPI, модульний моноліт; CA3 & Faculty Parser Task). Хостинг: Render/Railway (MVP) або сервер університету (`AGENTS.md`) | Наша інфраструктура, довірена |
| TZ-3 | Хостинг бази даних: Master DB (PostgreSQL), включно з файлами документів деканату. На Render/Railway — керована БД, доступна по мережі | Внутрішня зона, доступ лише з TZ-2 |
| TZ-4 | Треті сторони: Google Workspace SSO, External LLM API | Напівдовірені провайдери поза контролем команди |
| TZ-4 | Треті сторони: САЗ НаУКМА, сайт факультету | Недовірений вміст (скрапінг) |

| Межа | Звідки → куди | Що перетинає (сутності) | Пріоритет |
|---|---|---|---|
| **TB1** | TZ-1 → TZ-2 (React SPA → Application Server; HTTPS, REST/JSON, Bearer JWT) | JWT, `StudentProfile`, `PlanPreferences`, `IndividualPlan`, файли `DeaneryPlanDocument`, дії адміна | 1 |
| **TB7** | TZ-2 ↔ TZ-4 (Profile Service ↔ САЗ від імені студента, кнопка «Оновити») | Затверджений `IndividualPlan`, облікові дані САЗ | 2 |
| **TB4** | TZ-2 → TZ-4 (AI Recommendation Adapter → External LLM API) | Напрямки, навантаження, агрегована власна історія планів (коди курсів), відфільтрований каталог. Без id і email студента (ADR-003) та без списку небажаних викладачів | 3 |
| **TB6** | Всередині TZ-2: роль student → адмін-функції (Ingestion & Moderation, запуск Parser Task; логічна межа привілеїв) | `SyncJob`, `ModerationItem`, `Direction`, `CertificateProgram` | 4 |
| **TB2** | TZ-2 → TZ-3 (Application Server / Parser Task → PostgreSQL; TCP/IP, asyncpg) | Усі сутності, файли документів | 5 |
| **TB3** | TZ-2 ↔ TZ-4 (Auth Service ↔ Google SSO) | Ідентичність (`User.email`, `google_sub`) | 6 |
| **TB5** | TZ-4 → TZ-2 (САЗ / сайт факультету → Parser) | `Course`, `CertificateProgram` (цілісність) | 7 |

Пріоритет визначено за чутливістю даних, що перетинають межу («Do: починайте з меж, які перетинають чутливі дані»).

> **TB6 і TB7 відсутні в первинній `deployment-old.puml` і додані в `uml/deployment.puml`.** TB6 — логічна межа (не мережева): адмін-функції працюють у тому ж Application Server, тому межа проходить по перевірці ролі, а не між вузлами. TB7: функція «Оновити» (автосинхронізація затвердженого плану з САЗ) описана в `Project-Description.md`, але на діаграмах є тільки публічний скрапінг каталогу (TB5). Отримати *особистий* план студента з САЗ без його автентифікації неможливо, тому це окрема межа — див. R14.

## 3. STRIDE по межах

Позначки: **S** Spoofing, **T** Tampering, **R** Repudiation, **I** Information Disclosure, **D** Denial of Service, **E** Elevation of Privilege. «—» означає, що загрозу розглянуто і визнано неактуальною (з поясненням).

### TB1 — Web Browser / React SPA (TZ-1) → Application Server (TZ-2)

| | Питання | Відповідь |
|---|---|---|
| S | Чи може хтось видати себе за іншого? | Так: викрадення JWT через XSS (назва/опис курсу із САЗ, відрендерений як HTML) → **R7** |
| T | Чи можна змінити дані в дорозі/у сховищі? | У дорозі — ні (HTTPS). Але клієнт контролює тіло запиту: `course_year` / лічильники в `PATCH /profile` → **R15**; заміна на `PlanAlternative` з перевищенням 25 кредитів (FR-010), 4-й напрямок (FR-007) → серверна валідація, **R15**; підроблений `DeaneryPlanDocument` → **R8** |
| R | Чи може учасник заперечити дію? | Так: студент заперечує зміну плану, адмін — схвалення `ModerationItem` → **R9** |
| I | Чи можуть дані витекти? | Так: IDOR на `IndividualPlan`, `DeaneryPlanDocument`, `PlanPreferences` → **R3**; Bearer JWT, доступний JavaScript, викрадається через XSS → **R7** |
| D | Чи можна вивести з ладу навантаженням? | Так: важкі PDF/Docx → **R4**; масові `POST /plans/generate` — синхронний запит тримає worker до 3 × ~90 с (`sequence-generate-plan.puml`) → **R10** |
| E | Чи можна отримати зайві права? | Так: студент викликає адмінські ендпойнти напряму → **R2**; студент 4 курсу обходить FR-003 → **R15** |

### TB7 — Student Profile Service ↔ САЗ (від імені студента, «Оновити»)

| | Питання | Відповідь |
|---|---|---|
| S | Видати себе за іншого? | Якщо платформа зберігає логін/пароль САЗ студентів, будь-хто з доступом до БД/логів може увійти в САЗ як студент → **R14** |
| T | Змінити дані? | Затверджений план імпортується з `origin = saz_sync`; якщо студент може надіслати «результат синхронізації» з клієнта, він підмінить затверджений план і лічильники → **R15** |
| R | Заперечити дію? | Студент заперечує, що синхронізація відбувалась → запис у `AuditLog` (**R9**) |
| I | Витік? | Облікові дані САЗ — доступ до всього академічного профілю студента в САЗ, не лише до плану → **R14** |
| D | Вивести з ладу? | Масове натискання «Оновити» → платформа генерує потік запитів до САЗ від свого IP; САЗ блокує IP, ламається й парсинг каталогу → **R14** (ліміт 1 синхронізація / 10 хв на студента) |
| E | Зайві права? | Зберігаючи сесію/пароль САЗ, платформа отримує більше прав, ніж потрібно (запис на курси, особисті дані) → **R14** |

### TB4 — AI Recommendation Adapter → External LLM API

| | Питання | Відповідь |
|---|---|---|
| S | Видати себе за іншого? | Витік API-ключа LLM із репозиторію → хтось інший використовує акаунт проєкту → **R10** |
| T | Змінити дані? | Prompt injection через `Course.description` зі САЗ/сайту факультету; галюцинації: неіснуючі курси, курси небажаних викладачів (FR-005), перевищення ліміту 25 → **R5** |
| R | Заперечити дію? | Студент заявляє, що AI порадив неправильний план → `AIGenerationRequest` (модель, хеш prompt, час) + **R9** |
| I | Витік даних? | **Головний ризик межі**: sequence-діаграма передбачає крок «побудувати анонімізований контекст (без ID та email, ADR-003)», але якщо його реалізовано через серіалізацію ORM-об'єктів, у prompt потрапляють `User.email`, `full_name`, `DeaneryPlanDocument` або дані інших студентів (порушення НФВ-3) → **R1** |
| D | Вивести з ладу? | Недоступність LLM → 3 спроби з таймаутом ~90 с, потім 503 (sequence) → **R11**; вичерпання квоти/бюджету, помножене на 3 спроби (REL-001) → **R10** |
| E | Отримати зайві права? | — AI Adapter має лише read-only доступ до каталогу; відповідь LLM не виконується як код і не пишеться в БД без валідації (контрзахід R5) |

### TB6 — Роль student → адмін-функції (логічна межа всередині Application Server)

| | Питання | Відповідь |
|---|---|---|
| S | Видати себе за адміна? | Роль з тіла запиту/заголовка замість `User.role` у БД чи підписаного JWT → **R2** |
| T | Змінити дані? | Схвалення зміненого `ModerationItem` або редагування `Direction` / `CertificateProgram` → зламаний каталог для всіх студентів → **R2**, **R13** |
| R | Заперечити дію? | Адмін заперечує схвалення / запуск парсингу; `SyncJob.initiated_by`, `ModerationItem.reviewed_by` + `AuditLog` → **R9** |
| I | Витік? | Адмін-роутер, доступний студенту, може віддавати дані всіх користувачів → **R2** |
| D | Вивести з ладу? | Багаторазовий запуск парсингу → паралельні `SyncJob` (до 30 хв кожен, PERF-002) → **R4** |
| E | Зайві права? | Так — **R2** |

### TB2 — Application Server / Parser Task (TZ-2) → Master DB (TZ-3)

| | Питання | Відповідь |
|---|---|---|
| S | Видати себе за іншого? | Спільний DB-користувач для всіх модулів: будь-який модуль «є» будь-яким іншим → **R12** |
| T | Змінити дані? | У дорозі: на Render/Railway (MVP) керована PostgreSQL доступна по мережі, тож SQL-трафік по TCP/IP без TLS можна перехопити й змінити → **R12** (`ssl=require` в asyncpg). У сховищі: SQL-ін'єкція через фільтри каталогу (напрямок, викладач, кредити); зміна чи видалення записів `AuditLog` → **R12**, **R9** |
| R | Заперечити дію? | `IndividualPlan.updated_at` перезаписується без історії → **R9** |
| I | Витік? | Бекап без шифрування містить `User` і файли `DeaneryPlanDocument.content`; «read-only» AI-модуль фактично має повний доступ → **R12** |
| D | Вивести з ладу? | Масовий upsert каталогу під час `SyncJob` блокує таблицю `Course` під час запису студентів → **R4** |
| E | Зайві права? | Компрометація Deanery Document Parser (шкідливий файл) = доступ до всієї БД → **R12** |

### TB3 — Auth Service ↔ Google Workspace SSO

| | Питання | Відповідь |
|---|---|---|
| S | Видати себе за іншого? | **Так**: без перевірки claim `hd` проходить особистий Gmail; `email.endswith("ukma.edu.ua")` пропускає `x@evilukma.edu.ua`; без перевірки `aud` приймається токен іншого застосунку (FR-012) → **R6** |
| T | Змінити дані? | Підміна ID-token — ні (підпис Google). Відсутність `state`/PKCE → login CSRF → **R6** |
| R | Заперечити дію? | — вхід фіксується і в Google Workspace (аудит домену НаУКМА), і в `AuditLog` |
| I | Витік? | Запит зайвих scopes (Drive, Calendar) → лише `openid email profile` (частина R6) |
| D | Вивести з ладу? | Недоступність Google SSO → **R11** |
| E | Зайві права? | Роль `admin` призначається за email у конфігу → помилка/підміна; роль лише в `User.role`, змінюється іншим адміном → **R2** |

### TB5 — САЗ / сайт факультету → CA3 & Faculty Parser Task

| | Питання | Відповідь |
|---|---|---|
| S | Видати себе за джерело? | Скрапінг по HTTP(S) (`deployment.puml`): якщо джерело доступне лише по HTTP або сертифікат не перевіряється — DNS-spoofing / MITM → **R13** |
| T | Змінити дані? | MITM змінює `Course.credits`/`trimester`; шкідливий текст в описі курсу → **R13**, **R5**, **R7** |
| R | Заперечити дію? | Неможливо довести, що саме повернуло джерело → `SyncJob.raw_snapshot` + `raw_snapshot_sha256` (**R13**) |
| I | Витік? | — скрапінг публічних сторінок без автентифікації (на відміну від TB7) |
| D | Вивести з ладу? | Зміна верстки / недоступність → `SyncJob.status = failed` → **R11** |
| E | Зайві права? | — Parser пише лише в `ModerationItem`; у `Course` дані потрапляють після схвалення адміна (FR-008) |

|---|---|---|---|---|---|---|
| React SPA: student UI (TZ-1) | Викрадення JWT (R7) | Підміна JSON/файлів (R8, R15) | Заперечення змін плану (R9) | XSS читає дані сторінки (R7) | — навантаження лягає на сервер | Приховані кнопки ≠ захист (R2) |

| Application Server: Catalog / Certificate Service | — | SQL-ін'єкція у фільтрах (R12) | — | — публічні дані | Фільтри без пагінації проти НФВ-1 (R4) | — |
| Sync Orchestrator + CA3 & Faculty Parser Task (TZ-2) | Підміна джерела (R13) | MITM по HTTP (R13) | Сирий знімок (R13) | — | Паралельні `SyncJob` (R4), зміна верстки (R11) | Роути без ролі (R2) |

## 5. Реєстр ризиків

Оцінка = ймовірність × вплив. **Висока**: ймовірно і шкодить PII або даним багатьох користувачів. **Середня**: потребує специфічних умов або шкода обмежена. **Низька**: малоймовірно або шкода незначна.

### Підсумок

- Задокументовано **15** ризиків: високих — 5 (R1, R2, R3, R4, R14), середніх — 9, низьких — 1.
- Свідомо прийняті ризики: **R8**, **R11**; частково — **R12**, **R13**.
- Відкрите питання для команди: **R14** — як реалізувати «Оновити» без зберігання облікових даних САЗ. Після рішення уточнити зв'язок TB7 в `uml/deployment.puml` і додати його в `component-diagram.plantuml`.
- Відкрите питання щодо архітектури: `AGENTS.md` описує **3 незалежні сервіси** (core backend, SAZ parser, recommendation service з read-only доступом до БД), а `uml/deployment.puml` і `component-diagram.plantuml` — модульний моноліт в одному контейнері. Модель загроз побудована для моноліту. Якщо recommendation service стане окремим сервісом, з'явиться нова мережева межа core backend ↔ recommendation service (автентифікація між сервісами), а окрема DB-роль `ai_readonly` з R12 стане обов'язковою.
- Розбіжності з `sequence-generate-plan.puml`, які варто внести в діаграму: перевірка `saz_code` відповіді LLM за каталогом (R5), запис в `AuditLog` (SEC-001, R9), ліміт активних генерацій (R10).
- Першочергові контрзаходи перед релізом: R1, R2, R3, R4, R15 (серверна валідація лімітів уже вимагається в `requirements.md`, розділ «Припущення та обмеження»).
