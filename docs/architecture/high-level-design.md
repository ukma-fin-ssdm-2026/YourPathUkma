# High-Level Architecture Design: YourPathUkma

## 1. Межі системи

### Межі системи (Scope)
**Входить у межі поточного обсягу:**
- Автентифікація виключно через корпоративний Google Workspace SSO НаУКМА (`@ukma.edu.ua`).
- Особистий кабінет студента з трекінгом лімітів кредитів (240 сумарно, 25 вільного вибору, 54 профорієнтовні) та історією планів.
- Завантаження та парсинг офіційного документа нормативних дисциплін деканату (`DeaneryPlanDocument`).
- Конструктор плану з вибором рівня тижневого навантаження (низьке, середнє, високе) за триместрами та перевіркою конфліктів.
- AI-генерація навчального плану (з поясненнями та 2–3 альтернативами) на базі каталогу та унікальних фільтрів.
- Асинхронний парсинг каталогу дисциплін САЗ та сертифікатних програм факультету.
- Адміністративна панель для керування запуском скрейпінгу, чергою модерації та довідниками.

**Поза межами системи (Out-of-scope):**
- Пряме подання заявки та автоматичний запис у САЗ (платформа є допоміжним інструментом для орієнтації).
- Формування планів для студентів 1-го курсу (повністю регулюється деканатом).
- Збереження та модерація відгуків про викладачів/курси (надається лише зовнішнє посилання).
- Робочі кабінети працівників деканату.

## 2. Архітектурний стиль
Для системи обрано стиль **модульного моноліта (Modular Monolith)** на базі FastAPI (Python) з клієнтським застосунком React SPA та реляційною СУБД PostgreSQL.

**Обґрунтування вибору:**
- **Простота розгортання та експлуатації:** Єдиний монолітний артефакт бекенду в Docker-контейнері суттєво знижує накладні витрати на інфраструктуру у порівнянні з мікросервісами в умовах обмеженого часу команди.
- **Атомарність та транзакційна цілісність:** Усі операції перевірки лімітів (240 кредитів за 4 роки, ліміт 25 кредитів вільного вибору) та збереження індивідуального плану виконуються в межах ACID-транзакцій однієї бази даних.
- **Локальна ізоляція доменів:** Функціонал розділено на слабко зв'язані внутрішні пакети (модулі). Комунікація між модулями реалізована через строгі in-memory інтерфейси мови програмування без мережевого оверхеду.
- **Масштабованість в майбутньому:** При бажанні розширювати систему динамічно в майбутньому можна буде винести окремі модулі в окремі сервіси, що дасть можливість безболісно перейти на більш гнучкі архітектурні рішення SOA/Microservices.

## 3. Декомпозиція та опис компонентів
[Діаграма компонентів системи](uml/svg/component-diagram.svg) ([вихідний код цієї діаграми](uml/component-diagram.plantuml))

### 3.1. Рівень представлення (Client Tier)
- **Student Dashboard & Profile:** відображення прогресу виконання кредитної програми, історії збережених планів та синхронізація із САЗ.
- **Plan Builder UI:** конструктор планування, інтерактивний розподіл вибіркових курсів по триместрах, конфігурація побажань (до 3 напрямків, небажані викладачі, сертифікати).
- **Deanery Doc Uploader:** інтерфейс завантаження документа нормативних дисциплін (PDF/DOCX).
- **Catalog & Certificates View:** перегляд каталогу курсів із фільтрацією та перевіркою доступності сертифікатних програм.
- **Admin Console:** панель адміністратора для моніторингу `SyncJob`, ручного запуску скрейпінгу та модерації оновлених дисциплін.

### 3.2. Рівень застосунку (Application Tier — Modular Monolith)
- **Auth & User Module:**
  - `Auth Service`: перевірка JWT-токенів Google Workspace OAuth2, валідація приналежності домену `@ukma.edu.ua`, контроль доступу за ролями.
  - `Student Profile Service`: управління профілем студента, динамічний підрахунок використаних та залишкових кредитів.
- **Planning & Validation Module:**
  - `Study Plan Service`: координація створення, збереження та оновлення планів.
  - `Academic Validation Engine`: ядро серверної валідації академічних правил (авторозрахунок залишку для 4 курсу, контроль вільного вибору $\le 25$ кредитів, діапазон 57–60 кредитів/рік).
  - `Deanery Document Parser`: видобування нормативних дисциплін із файлів деканату для виключення конфліктів у конструкторі.
- **Recommendation Module:**
  - `AI Recommendation Adapter`: побудова анонімізованого контексту для зовнішнього LLM API, виключення небажаних викладачів, генерація альтернатив та retry при відмові провайдера.
- **Catalog & Certificates Module:**
  - `Catalog Service`: надання доступу до затвердженого переліку дисциплін, фільтрація та пошук.
  - `Certificate Program Service`: case-insensitive звірка дисциплін сертифікатних програм із сайту ФІ проти каталогу САЗ.
- **Ingestion & Moderation Module:**
  - `Sync Orchestrator`: керування життєвим циклом завдань `SyncJob`, відстеження помилок.
  - `CA3 & Faculty Parser Task`: асинхронні фонові задачі (Background Tasks) для скрейпінгу.

### 3.3. Рівень даних (Data Tier)
- **PostgreSQL:** єдине джерело правди системи. Містить реляційні таблиці користувачів, планів, чернеток, нормативних і вибіркових курсів, сертифікатів, журналу `SyncJob` та буферної черги модерації (Moderation Queue).

## 6. Інтерфейси взаємодії

| Інтерфейс / Потік | Тип взаємодії | Протокол / Формат | Призначення |
|---|---|---|---|
| **Client $\leftrightarrow$ Backend Core** | Синхронний, мережевий | HTTPS, REST API (JSON) | Виконання клієнтських операцій за наявності Bearer JWT |
| **Backend $\leftrightarrow$ Google SSO** | Синхронний, зовнішній | HTTPS / OAuth2 (OIDC) | Перевірка автентичності студента та домену |
| **Backend $\leftrightarrow$ External LLM API** | Синхронний/Потоковий, зовнішній | HTTPS POST (JSON) | Передача анонімізованого промпту та отримання плану |
| **Parser Task $\leftrightarrow$ САЗ / Сайт ФІ** | Асинхронний, зовнішній | HTTP/HTTPS (HTML scraping)| Викачування сторінок каталогу САЗ та програм факультету |
| **Core Modules $\leftrightarrow$ PostgreSQL** | Синхронний, внутрішній | TCP/IP (SQL, `asyncpg`) | Читання та запис доменних даних |
| **Внутрішньомодульні виклики** | Синхронні / асинхронні | Python Protocols (in-process) | Обмін даними між доменами моноліта у спільній пам'яті |
