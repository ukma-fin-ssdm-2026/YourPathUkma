4. Відкриття PR
5. Схвалення учасниками
6. Закриття дедлайну

### 4.1 Практики інженерії вимог
- **Перегляд користувацьких історій:** Усі історії проходять обов'язкове командне рецензування та перевірку за евристикою INVEST і критеріями прийняття перед злиттям у гілку `main`.

- **Управління артефактами:** Усі файли вимог (`requirements.md`, `user-stories.md`, `rtm.md`, `use-cases.md`) зберігаються виключно в директорії `/docs/requirements/` репозиторію. У головному `README.md` підтримується актуальний розділ з посиланнями на них.

## 5. Вирішення конфліктів

1. **Порушення етики спілкування** — розмова з командою та попередження. За повторення — припинення співпраці, обов'язки розподіляються між рештою учасників.

2. **Технічні розбіжності** («як краще зробити?», «що використати?») — голосування, рішення більшості. Якщо рішення виявилось помилковим — команда вирішує шляхом нового голосування; виправленням займаються ті, хто голосував «за».

3. **Перенавантаження учасника** — волонтер може взяти частину тасок. Якщо волонтера немає — надлишок розподіляється рівномірно або перевантаженому значно зменшується навантаження при наступному розподілі (вибір за постраждалим). У крайньому випадку, якщо команда визнає це помилкою планування Issue Tracker Lead — надлишкові завдання виконує він.

4. **Пропуск дедлайнів або халатне ставлення** — організовується зустріч-розмова з учасником; за потреби проводиться голосування щодо подальшої співпраці.

## 7. Етична та професійна поведінка

### 7.1 Взаємоповага та культура

- **Інклюзивність і толерантність:** усі учасники ставляться одне до одного з повагою незалежно від досвіду, поглядів чи особистих особливостей. Дискримінація, булінг, агресія та перехід на особистості — неприпустимі.
- **Конструктивна критика:** під час code review та обговорень фокус — на коді та задачах, а не на авторі. Зауваження подаються в обґрунтованій, ввічливій та конструктивній формі.

### 7.2 Академічна та професійна доброчесність

- **Авторські права:** забороняється використовувати чужий код без зазначення джерел або ліцензій.
- **Чесність у звітності:** дані про прогрес, статус тестів та метрики мають бути достовірними. Приховування помилок або дедлайнів — заборонено.
- **Стандарти:** усі учасники дотримуються академічної доброчесності та [Кодексу етики ACM](https://www.acm.org/code-of-ethics).

### 7.3 Відповідальність та командна робота

- **Своєчасність:** учасники зобов'язані вчасно повідомляти про затримки та ризики. Важливі архітектурні зміни узгоджуються з командою.
- **Якість:** кожен розробник відповідає за якість свого коду, проходження базового тестування та оформлення PR відповідно до прийнятих стандартів.

## 8. Використання ШІ

**Дозволені інструменти:**
- Асистенти для написання коду та автодоповнення (GitHub Copilot, Cursor — на вибір кожного учасника)
- Чат-моделі (Gemini, ChatGPT) для генерації ідей, обговорення архітектури та пошуку помилок

**Правило верифікації:** весь згенерований ШІ-код підлягає обов'язковій перевірці: локальне тестування, статичний аналіз та code review через PR. Неперевірений або «вайб-кодинговий» код **суворо заборонено** зливати в основну гілку.

**Прозорість:** кожен артефакт містить нотатку «Використання ШІ» із зазначенням, які частини створено за допомогою ШІ та як вони перевірені.

**Особиста відповідальність:** кожен учасник повністю відповідає за кожен рядок зданого коду та зобов'язується пояснити його логіку за pytest/тестами за потреби.

## 10. Політика якості та огляду коду

### 10.1 Стандарт кодування

- **Мова та стиль:** Python; код відповідає [PEP 8](https://peps.python.org/pep-0008/). Максимальна довжина рядка — 88 символів (стандарт Black).
- **Найменування:** `snake_case` для функцій і змінних, `PascalCase` для класів, `UPPER_SNAKE_CASE` для констант. Назви англійською, осмислені, без одно-літерних імен (окрім лічильників циклів).
- **Типізація:** усі публічні функції та методи мають анотації типів (type hints).
- **Документація в коді:** публічні модулі, класи та функції мають docstring (стиль Google або NumPy — єдиний для всього проєкту). Коментарі пояснюють «чому», а не «що».
- **Принципи проєктування:** код дотримується принципів SOLID (відповідно до назви команди): одна відповідальність на клас/модуль, залежність від абстракцій, відсутність дублювання (DRY). Функції — короткі та з однією метою.
- **Структура проєкту:** вихідний код, тести та документація розділені (`src/`, `tests/`, `docs/`). Секрети та ключі не комітяться; використовуються змінні середовища та `.gitignore`.
- **Повідомлення комітів:** формат [Conventional Commits](https://www.conventionalcommits.org/) (`feat:`, `fix:`, `docs:`, `test:`, `refactor:`, `chore:`), імперативний спосіб, до 72 символів у заголовку.
- **Назви гілок:** `feature/<короткий-опис>`, `fix/<короткий-опис>`, `docs/<короткий-опис>`; за потреби з номером Issue (`feature/12-login-form`).

### 10.2 Обов'язкові інструменти

| Призначення | Інструмент | Вимога |
|---|---|---|
| Форматування | Black | Код відформатовано без змін при повторному запуску |
| Лінтинг | Ruff (або flake8) | 0 помилок і попереджень |
| Статична типізація | mypy | 0 помилок у `src/` |
| Тестування | pytest + pytest-cov | Усі тести проходять; покриття нового коду ≥ **80%** |
| Pre-commit | pre-commit hooks | Black, Ruff і перевірка зайвих пробілів/кінця файлу запускаються перед кожним комітом |
| CI | GitHub Actions | Pipeline (форматування, лінтинг, mypy, тести) має бути зеленим; PR із червоним CI не зливається |
| Керування залежностями | `requirements.txt` / `pyproject.toml` | Усі нові залежності зафіксовано та обґрунтовано в PR |

Конфігурація інструментів зберігається в репозиторії (`pyproject.toml`, `.pre-commit-config.yaml`, `.github/workflows/`), щоб правила були однаковими в усіх учасників та в CI. Для локального статичного аналізу ШІ-згенерованого коду (розділ 8) використовуються ті самі інструменти.

### 10.3 Кроки огляду коду колегою

1. **Підготовка автора.** Автор синхронізує гілку з `main`, локально запускає форматування, лінтинг, mypy і тести та переконується, що вони проходять.
2. **Відкриття PR.** До **середи 12:00** автор відкриває PR за шаблоном: що змінено і чому, посилання на Issue / вимогу (ID у `rtm.md`), як перевірено, нотатка «Використання ШІ», чек-лист Definition of Done. PR має бути невеликим та зосередженим на одній задачі.
3. **Автоматичні перевірки.** Запускається CI. До успішного проходження CI рев'ювери не починають змістовний огляд.
4. **Призначення рев'юверів.** Рев'юерами є всі інші учасники команди (згідно з правилом схвалення усіма). Автор не схвалює власний PR.
5. **Огляд.** Рев'юер перевіряє:
   - відповідність вимогам, користувацьким історіям і критеріям прийняття;
   - коректність логіки, обробку помилок і граничних випадків;
   - дотримання стандарту кодування та принципів SOLID;
   - якість і достатність тестів;
   - відсутність секретів, зайвого коду та неперевіреного ШІ-коду;
   - актуальність документації.
6. **Коментарі.** Зауваження конструктивні, обґрунтовані та стосуються коду, а не автора (див. 7.1). Рев'юер позначає, що є блокуючим (`must`), а що — побажанням (`nit` / `suggestion`).
7. **Виправлення.** Автор відповідає на кожен коментар: виправляє або аргументує відмову. Нові коміти додаються в ту саму гілку; рев'юер повторно перевіряє лише змінені місця.
8. **Схвалення.** Рев'юер залишає Approve у GitHub. Усі схвалення — до **середи 18:00** (якщо одного немає до 21:00 — PR все одно публікується, див. розділ 4).
9. **Злиття.** Після схвалень і зеленого CI автор (або Супроводжувач репозиторію) зливає PR у `main` через squash/merge до **четверга 10:00** та видаляє гілку. Прямі коміти в `main` заборонені.
10. **Ретроспектива.** Повторювані зауваження обговорюються на суботній зустрічі й, за потреби, додаються до стандарту кодування або чек-листа.

### 10.5 Критерії готовності коду (Definition of Done)

Завдання вважається виконаним, лише якщо виконано **всі** пункти:

**Код**
- [ ] Реалізовано всі критерії прийняття відповідної користувацької історії / вимоги.
- [ ] Код відповідає стандарту кодування (10.1); Black, Ruff і mypy проходять без помилок.
- [ ] Відсутні закоментований код, `print`-налагодження, TODO без прив'язки до Issue, секрети та ключі.
- [ ] Публічні функції та класи мають type hints і docstring.

**Тестування**
- [ ] Написано unit-тести (pytest) для нової логіки, включно з негативними та граничними випадками.
- [ ] Усі тести (нові та наявні) проходять локально та в CI.
- [ ] Покриття нового коду ≥ 80%.

**Огляд і інтеграція**
- [ ] PR відкрито за шаблоном і пов'язано з Issue.
- [ ] CI зелений.
- [ ] Отримано схвалення від усіх учасників (з урахуванням правила дедлайну з розділу 4).
- [ ] Усі блокуючі коментарі закрито.
- [ ] Гілка актуальна відносно `main`, конфліктів немає.

**Документація та простежуваність**
- [ ] Оновлено документацію (`README.md`, `docs/`), якщо змінилась поведінка чи спосіб запуску.
- [ ] Оновлено `rtm.md`: вимога → код → тест.
- [ ] Артефакт містить нотатку «Використання ШІ» (які частини створено ШІ та як перевірено), див. розділ 8.
- [ ] Автор може пояснити логіку кожного рядка свого коду.

**Закриття**
- [ ] PR злито в `main`, Issue закрито, гілку видалено.
- [ ] Для лабораторних — додано посилання на індивідуальне Loom-відео (розділ 9).
